# БЭМ-аудитор макетов (Figma)

## When to Use / Когда триггерить

Пользователь просит: проверить/починить названия слоёв или компонентов в Figma-макете, привести слои к БЭМ, проаудировать макет перед вёрсткой, «что не так с неймингом в этом фрейме», подобрать корректные имена элементам разметки, спрашивает правила именования БЭМ (block/element/modifier, `__`, `_`, `--`), спрашивает классы/состояния UIkit (`uk-button-primary`, `uk-active`, `uk-open`). Также — при словах «БЭМ», «bem», «ui kit», «уйкит», «нейминг слоёв», «переименуй фреймы» в контексте макета. И когда агент сам создаёт слои в Figma (примеры, компоненты, сборка макета) — имена расставляются сразу по схеме, см. «Нейминг при создании», не дожидаясь напоминания.

## Три режима

| Режим | Вход | Что делает |
|---|---|---|
| **Справочник** | вопрос без ссылки на макет | Отвечает ТОЛЬКО по `references/bem-naming.md` и `references/uikit.md`. Нет факта в справочнике — так и сказать, не додумывать |
| **Аудит** | ссылка на Figma (фрейм/страницу) | Дерево слоёв → неадекватные имена → таблица корректур. НИЧЕГО не меняет |
| **Переименование** | утверждённый список корректур | Применяет переименования через `use_figma`, пачками с верификацией |

## Железные правила

1. **Ни одного переименования без явного «да» пользователя** на конкретный список. «Посмотри макет» ≠ разрешение править. Утверждается вся таблица или её части («кроме строк 5, 12» — тоже ответ).
2. **Только факты.** Правила БЭМ и имена UIkit берутся из reference-файлов (в них — источники и даты извлечения). Формулировка «в БЭМ принято…» без опоры на справочник запрещена. Если вопроса нет в справочнике — сказать прямо и предложить свериться с источником, а не выдумывать.
3. **Одна схема на проект.** Перед первым аудитом спросить: `classic` (bem.info: `block__el_mod_val`) или `two-dashes` (getbem: `block__el--mod--val`). Если в дереве уже есть БЭМ-имена — определить используемую схему по ним и не предлагать миграцию без спроса.
4. Правка — `node.name` + wrapper-ФРЕЙМ (обёртка вокруг sibling-слоёв: plain frame, `layoutMode="NONE"`, техника и верификация в `references/figma-workflow.md`) + группировка в GROUP и именование групп (организационная операция, визуал не ломает). **ЗАПРЕЩЕНО: проставлять/менять `layoutMode≠NONE`, `layoutWrap`, itemSpacing — любой auto-layout** (расставляет только пользователь руками: эксперимент с wrap-галереей стоил потери всех её узлов) и **перестраивать существующие группы/фреймы (group→frame с репартингом детей) вне wrapper-техники**. **Никогда не удалять контейнер, не проверив детей** — `remove()` сносит содержимое целиком (так и потеряли галерею: «чистка сироты» съела уже перенесённых детей; пустая группа удаляется сама, явный `remove()` кинет безвредную «node does not exist» — не ретраить destructive-кодом). Не трогать `characters` текстовых узлов, содержимое инстансов внешних библиотек, имена переменных/стилей (если не просят отдельно).
5. Все ответы пользователю — на русском.
6. Различать режимы: пользователь мог попросить только справочник — не тащить в ответ Figma-вызовы; и наоборот.

## Workflow аудита

### Шаг 1. Доступ и объём

URL вида `figma.com/design/<fileKey>/…?node-id=<i>-<j>` → `fileKey`, `nodeId` (`-` заменить на `:`). Если ссылки нет — спросить; если пользователь описывает макет словами — режим справочника.

Загрузить skill `figma-use` **до** любого вызова `use_figma` (обязательное требование инструмента; передавать `skillNames: "figma-use"`).

### Шаг 2. Снимок дерева

Сначала `get_metadata(fileKey, nodeId)` — обзор структуры. Для полного списка имён с типами и иерархией — `use_figma` read-only скрипт «Dump tree» из `references/figma-workflow.md`. Многостраничный аудит: один вызов `use_figma` на страницу, все N вызовов — в одном сообщении параллельно (правило figma-use: не более одной смены страницы на вызов).

### Шаг 3. Детект мусора (детерминированно)

Все имена слоёв выгрузить в `names.txt` и прогнать через харнесс — глазами только спорные случаи, не весь список:

```bash
cat names.txt | python3 scripts/validate_bem_name.py --scheme classic --figma
```

- `auto_generated: true` = имя автогенерации Figma (`Frame 12`, `Vector`, `Group 3`, `Union 2`, `Rectangle 214`) — приоритет номер один на переименование.
- `errors` непустой = невалидное БЭМ-имя (элемент элемента, `--` в classic-схеме, кириллица, CamelCase, лишние разделители).
- `warnings` (префикс `b-`) — в список корректур с пометкой «низкий приоритет».
- Уже валидные БЭМ-имена не трогать. Имена-исключения (содержательные на русском в служебных фреймах, `logo`, `icon-plus`) — оставлять с пометкой «на усмотрение».

### Шаг 4. Семантика для новых имён

Имя описывает РОЛЬ, а не содержимое или визуал: ✅ `notice_type_error`, ❌ `red-text`, ❌ `frame-1-copy`. Для спорных узлов — `get_screenshot(fileKey, nodeId)` плюс чтение `characters` (читать можно, менять нельзя). Дубли (три `Frame 45` рядом) называть по смыслу (`card__image`, `card__title`, `card__text`), а не `copy 1/2/3`. Готовые шаблоны имён типовых элементов макета — в `references/bem-naming.md` (раздел «Шаблоны»). Не переименовывать в псевдобэм: если узел — декоративная подложка без семантики, честнее предложить `card__bg`, чем вымученный модификатор.

**Три обязательных правила привязки к фактам дизайна** (нарушение = поток `__title` на всё и `__decor` на картинки, как в первом боевом прогоне):
1. **Префикс имени — СЕКЦИЯ, не страница.** Секция = БЛОК, дальше классическая схема `<блок>__<элемент>`: `hero__image`, `hero__heading-h2`, `booking__amenities-item`. Имена артбордов/страниц (`main-page__…`) блоком быть НЕ должны — это подмена блока страницей. Секций в Figma нет — определить по содержимому (`get_screenshot`) и спросить пользователя; следующий макет будет с секциями — брать их имена.
2. Текст — именовать по **текстовому стилю** узла (`textStyleId` → `H2` → `hero__heading-h2`, `Descripter` → `booking__descripter`); угадывать title/subtitle по кеглю нельзя, если стиль не прочитан.
3. `image` — для слоёв с IMAGE-fill (фото, растр): `hero__image`; `decor` — только векторы/текстуры/подложки. Проверка: `fills.some(f=>f.type==='IMAGE')`.
4. **Конфликт геометрии**: после генерации плана — группировка по имени и сравнение w/h; одноимённые элементы с разным соотношением сторон получают модификатор `_horz`/`_vert`/`_sq` (`relevant__card-image_vert`). Прогонять всегда, даже когда пользователь не указал на проблему.
5. **Части одного элемента — wrapper-фрейм**: если несколько одноимённых слоёв — части одного логического элемента (разрезанный для переноса заголовок, заголовок + подзаголовок в одном визуальном блоке), создать wrapper-фрейм `<блок>__<элемент>-wrap` (`relevant__heading-h2-wrap`), части сохраняют имя элемента. Фрейм — plain (`layoutMode="NONE"`, прозрачный), НЕ группа (по решению пользователя: фрейм тоже не ломает визуал и ближе к DOM-контейнеру). Отличать от независимых экземпляров (три карточки — НЕ обёртка, а элемент-блоки `<блок>__card`). Техника создания и верификация — в `references/figma-workflow.md`.
6. **Инстансы компонентов — НЕ элементы секции.** Слой `INSTANCE` (`mainComponent` не null) — самостоятельный блок: имя = имя его компонент-сета, транслит lowercase-hyphen (`logo`, `book-now`), БЕЗ секционного префикса и без `__` от секции. Префикс от секции инстансу ставить нельзя даже если он стоит внутри секции — это ломает переиспользование (тест «можно перенести — блок» из quick-start). Связь с секцией в разметке — микс `class="logo hero__logo"`, в Figma-слое это только имя блока; при переименовании инстанса читать `mainComponent.parent.name` (сет) — не угадывать. ⚠️ Реальный промах: `logo`-инстанс стал `hero__navigation-logo` — исправлено после ревью пользователем.

**Правило предупреждений**: любое отступление от чистого БЭМ (wrapper-слои, не имеющие CSS-судьбы; Iconify-кадры; листья векторной графики) — проговаривать вслух в отчёте отдельным блоком «отступления», даже если пользователь не спрашивал.

Форма записи по умолчанию в проекте пользователя — **классическая**: `блок__элемент`, слова внутри имени через дефис (`hero__image`, `booking__amenities-item-text`, `hero__heading-display`). Зафиксировано после ревью пользователем: дефисная схема (`hero-image`) отвергнута — машина не отличает границу блока от элемента. Секция = блок; `__` ровно один, элементов элемента нет.

**Нейминг при создании.** Когда агент сам рисует новые слои в Figma, схема применяется в момент создания, а не переименованием постфактум: блок = секция/компонент, `__` ровно один, слова через дефис, инстанс называется именем своего компонент-сета без секционного префикса. Исключение: имена переменных/токенов в БЭМ НЕ переводятся — слаш-формат (`color/brand`) есть стандарт Style Dictionary и к именам слоёв не применяется.

### Шаг 5. UIkit-слой аудита

Сначала определить, макет на UIkit или нет:
- есть узлы/компоненты с именами `uk-*` → UIkit-макет, сверять по `references/uikit.md`;
- явных признаков нет → спросить пользователя: «Проект верстается на UIkit? Если да — имена слоёв стоит приводить к его конвенции».

UIkit-проверки:
1. Каждое `uk-*` имя должно существовать в официальном списке классов/модификаторов/состояний (`references/uikit.md`). Выдуманные (`uk-button-hover`, `uk-card-rounded`, `uk-animation-fade-out`) — флагить; в справочнике есть таблица частых выдумок.
2. Варианты компонент-сетов (`state=hover`, `size=large`) — легальный синтаксис Figma, НЕ CSS-классы. Не требовать их переименования ради мнимого соответствия; предлагать только при явном противоречии с реальным API или по желанию пользователя.
3. Вёрстка НЕ на UIkit → секцию пропустить, не навязывать.

### Шаг 6. Отчёт (формат фиксированный)

Таблица корректур — ровно этими колонками:

```
| узел (id) | тип | было | стало | почему |
```

В «почему» — ссылка на конкретное правило из справочника («элемент элемента запрещён», «auto Figma») или на несуществующий UIkit-класс. Отдельно списки: «✓ валидно, не трогаем», «? вопрос к пользователю». Закончить явным запросом: «Поменять N имён? Да / нет / частично (какие строки исключить)».

### Шаг 7. Применение (только после «да»)

`use_figma` скриптом «Rename batch» из `references/figma-workflow.md`: словарь `{nodeId: newName}`, ≤50 пар на вызов, обязательный `return` со `mutatedNodeIds` и `missing`. После каждого батча — verification: повторное чтение имён затронутых id и сверка с планом. Итог: «N переименовано, M пропущено (id не найден)» — `missing` не замалчивать.

## Справочник (режим 1)

Ответ строить по `references/bem-naming.md` (схемы, правила, антипаттерны, шаблоны имён по типам элементов макета) и `references/uikit.md` (классы, модификаторы, состояния, выдумки). Формат: правило → пример `было → стало` → источник. Конфликтные трактовки источников давать обеими сторонами (например, элементы элемента: в БЭМ запрещены, но DOM-вложенность элементов разрешена — см. bem.info/html «Nesting of elements»). Если компонент UIkit не покрыт справочником — честно сказать и дать ссылку `getuikit.com/docs/<component>` вместо догадок.

## Структура скилла

- `references/bem-naming.md` — канон именования, обе схемы, антипаттерны, шаблоны по элементам макета
- `references/uikit.md` — словарь UIkit 3 (извлечено с getuikit.com 2026-09-24)
- `references/figma-workflow.md` — готовые JS-скрипты: dump tree, rename batch; питфоллы MCP
- `scripts/validate_bem_name.py` — детерминированный валидатор имён (проверен на ~40 кейсах обеих схем)
