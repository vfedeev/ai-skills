## Когда использовать

- По брифу или запросу нужно провести глубокий анализ конкурентов.
- Нужны скриншоты конкурентов в трёх вьюпортах для Figma.
- Нужно заполнить таблицу конкурентного анализа по шаблону Апрок.

**Не использовать для:** заполнения брифа (breefing), мониторинга новостей (competitor-news-monitor), извлечения бренд-айдентики (brand-dna-extractor).

## Инструменты

| Инструмент | Назначение |
|------------|----------|
| `web_search` | Поиск конкурентов, актуальных данных |
| `web_extract` | Извлечение содержимого страниц |
| `execute_code` / `terminal` | Скриншоты через Playwright (headless Chromium) |
| `execute_code` | Упаковка архива, агрегация |
| `delegate_task` | Запуск субагентов (Веб-парсер, Критик). Поддерживает `model` override |
| `clarify` | Уточнения у пользователя |
| SearXNG (POST localhost:8888) | Веб-поиск с Яндексом для русскоязычных источников |
| Polza.ai API | Факт-чек через Gemini / Perplexity Sonar |

## Роли (multi-agent)

### 1. Директор (оркестратор)
- **Модель:** текущая модель чата
- **Задачи:**
  - Получить бриф, извлечь конкурентов
  - Делегировать Веб-парсерам сбор данных (параллельно)
  - Делегировать Фотографам скриншоты (по 1 на конкурента, параллельно с парсерами)
  - Получить отчёты от парсеров и архивы скриншотов от Фотографов
  - Вызвать Критика для проверки каждого отчёта (Критик делает факт-чек через web)
  - При замечаниях — отправить парсеру на доработку (макс. 3 круга)
  - Неподтверждённые данные пометить «требует проверки»
  - Заполнить итоговую таблицу по шаблону (колонку «Выводы» — сам Директор)
  - Приложить архив скриншотов от Фотографов к отчёту
  - Доставить результат
  - Предложить очистку временных файлов через clarify

### 2. Фотограф
- **Модель:** выбирается через clarify (см. Фаза 0)
- **Делегирование:** `delegate_task(goal=..., context=..., toolsets=["terminal","file"], model={"provider":"...","model":"..."})`
- **Запуск:** по 1 субагенту на конкурента (параллельно с парсерами и/или пока Критик проверяет)
- **Задачи:**
  - Для конкурента сделать скриншоты через Playwright (headless Chromium):
    - Desktop (1920×1080)
    - Tablet (768×1024)
    - Smartphone (375×812)
  - Сохранить с именами: `{domain}--{page_name}--{viewport}.png`
  - Вернуть пути к скриншотам Директору

**Скрипт скриншотов (Playwright):**
```python
import asyncio
from playwright.async_api import async_playwright

async def take_screenshots(url, domain, page_name, output_dir):
    viewports = [
        {"name": "desktop", "width": 1920, "height": 1080, "dsf": 1, "mobile": False},
        {"name": "tablet", "width": 768, "height": 1024, "dsf": 1, "mobile": False},
        {"name": "smartphone", "width": 375, "height": 812, "dsf": 1, "mobile": True},
    ]
    async with async_playwright() as p:
        for vp in viewports:
            browser = await p.chromium.launch(headless=True)  # отдельный браузер на каждый скрин
            page = await browser.new_page(
                viewport={"width": vp["width"], "height": vp["height"]},
                device_scale_factor=vp["dsf"],
                is_mobile=vp["mobile"]
            )
            await page.goto(url, wait_until="domcontentloaded", timeout=30000)
            await page.wait_for_timeout(2000)  # дождаться рендера
            path = f"{output_dir}/{domain}--{page_name}--{vp['name']}.png"
            await page.screenshot(path=path, full_page=True)  # полная страница
            await browser.close()
```

**Важно:** 
- `wait_until="domcontentloaded"` вместо `networkidle` —后者 таймаутит на тяжёлых страницах.
- `full_page=True` — полная страница, не только viewport.
- Отдельный `browser` на каждый скрин — GPU может крашнуться на тяжёлых страницах.
- DPR=1 для всех вьюпортов — иначе GPU crash на длинных лендингах.

**Пути и зависимости:** см. `references/setup.md`

### 3. Веб-парсер
- **Модель:** выбирается через clarify (см. Фаза 0)
- **Делегирование:** `delegate_task(goal=..., context=..., toolsets=["web"], model={"provider":"...","model":"..."})`
- **По 1 субагенту на конкурента** (при лимите — очередь по 2-3 параллельно)
- **Задачи:**
  - Обойти страницы из списка (выбранного через clarify): главная, о компании, контакты, услуги/каталог
  - Найти данные через `web_search` + `web_extract`
  - Заполнить все поля шаблона по конкуренту (кроме «Выводы» — это Директор)
  - Сохранить отчёт в `competitor_analysis_output/raw/{domain}.md`
  - Вернуть текст отчёта Директору

### 4. Критик
- **Модель:** текущая модель чата (или выбрать через clarify)
- **Вызов:** отдельный `delegate_task` от Директора, в context — текст отчёта парсера
- **Задачи:**
  - Проверить отчёт на галлюцинации и неточности
  - Все ли факты подтверждены источниками?
  - Нет ли выдуманных данных?
  - Заполнены ли все поля?
  - Проверить отчёт на наличие иероглифов (китайские, японские, корейские символы). Если найдены — заменить на русский эквивалент или удалить.
  - Сделать факт-чек критических данных (цены, контакты, УТП) через web_search
  - Вернуть Директору: «ОК» или список замечаний для доработки

### Паттерн проверки
```
Директор → парсер получает данные → Директор вызывает Критика
  → Критик ОК → данные в таблицу
  → Критик замечания → парсер дорабатывает → Директор снова вызывает Критика
  → (макс. 3 круга)
  → после 3 кругов: сомнительные данные помечаются «требует проверки»
```

## Workflow

### Фаза 0 — Инициализация

1. Получить бриф (файл или текст)
2. Извлечь список конкурентов (из брифа или спросить у пользователя)
3. Определить страницы для анализа через `clarify`:
   ```python
   pages = clarify(
     question="Какие страницы анализировать? (по умолчанию — главная)",
     choices=["Только главная", "Главная + О компании + Контакты + Каталог/Услуги/Магазин", "Другое (указать)"]
   )
   ```
   Если «Другое» — спросить конкретные URLs или пути.
   **Примечание:** если у конкурента нет каталога услуг, но есть магазин — снимаем магазин. Ищем ссылки вида `/catalog/`, `/shop/`, `/store/`, `/produkcziya/`, `/uslugi/`.
4. Выбрать модели для субагентов через `clarify` (только при первом запуске или если указанная модель недоступна):
   ```python
   parser_model = clarify(
     question="Модель для Веб-парсеров?",
     choices=["xiaomi/mimo-2.5", "Текущая модель (self)", "Другое (указать)"]
   )
   photographer_model = clarify(
     question="Модель для Фотографа?",
     choices=["xiaomi/mimo-2.5", "Текущая модель (self)", "Другое (указать)"]
   )
   ```
   Если «Другое» — спросить `provider:model`.
5. Создать `competitor_analysis_output/` с поддиректориями: `raw/`, `screenshots/`

### Фаза 1 — Параллельный сбор

Запустить параллельно:

**Веб-парсеры** (по 1 на конкурента):
```python
delegate_task(
  goal="Собрать данные о конкуренте {domain}. Заполнить все поля шаблона анализа.",
  context="URL: {url}. Страницы: {pages}. Шаблон: {template_fields}. Источники: web_search + web_extract.",
  toolsets=["web"],
  model={parser_model}  # из clarify
)
```

**Фотографы** (по 1 на конкурента, параллельно с парсерами):
```python
for domain, pages in competitors.items():
    delegate_task(
      goal=f"Сделать скриншоты конкурента {domain} в 3 вьюпортах через Playwright.",
      context=f"Страницы: {pages}. wait_until=domcontentloaded, timeout=30000, wait_for_timeout=2000. full_page=True. DPR=1. Отдельный browser на каждый скрин. Сохранить в screenshots/{domain}/.",
      toolsets=["terminal", "file"],
      model={photographer_model}
    )
```

**Директор может запускать несколько инстансов Фотографа параллельно** для снижения общей нагрузки и введения асинхронности:
1. **Параллельно с веб-парсерами** — Фотографы снимают скрины, пока парсеры собирают данные. Не блокируют друг друга.
2. **После получения отчётов от парсеров** — пока Критик проверяет отчёты и Директор заполняет таблицу, Фотографы доснимают оставшиеся страницы (если что-то упало) или упаковывают архив.

**Важно:** 
- Директор ОБЯЗАН передать Фотографу конкретные URLs страниц каждого конкурента в context (тот же список, что выбран через clarify). Фотограф не угадывает URLs.
- Каждый Фотограф — отдельный субагент на 1 конкурента. Не нужно запускать одного Фотографа на всех.
- При лимите concurrent — очередь по 2-3 парсера + 2-3 фотографа параллельно.

### Фаза 2 — Проверка Критиком

Для каждого отчёта:
```python
delegate_task(
  goal="Проверить отчёт конкурента {domain} на галлюцинации и неточности.",
  context="Отчёт:\n{report_text}\n\nПроверить: все ли факты подтверждены? Нет ли выдуманных данных? Заполнены ли все поля? Есть ли иероглифы?",
  toolsets=["web"]
)
```

- Если «ОК» — данные в таблицу
- Если замечания — отправить парсеру на доработку
- Макс. 3 круга. После 3 — пометить сомнительное как «⚠️ требует проверки»

### Фаза 3 — Сборка

1. Заполнить таблицу `templates/competitor_analysis_table.md` по каждому конкуренту
2. Колонку «Выводы» заполняет Директор (синтез по всем конкурентам)
3. Сохранить в `competitor_analysis_output/final_analysis.md`

### Фаза 4 — Доставка

1. Вывести итоговую таблицу в чат
2. Скинуть архив скриншотов от Фотографа (`MEDIA:`)
3. Сводка: сколько конкурентов, какие страницы, что найдено
4. Предложить очистку через `clarify`:
   ```python
   cleanup = clarify(
     question="Удалить кэш и временные файлы скилла?",     choices=["Да, удалить", "Нет, оставить"]
   )
   ```
   Если «Да» — удалить:
   - `competitor_analysis_output/screenshots/` (PNG-исходники, уже в архиве)
   - `competitor_analysis_output/raw/` (черновики парсеров)
   - `~/.hermes/cache/delegation/live/{delegation_id}/` (логи субагентов текущего запуска)
   - `~/.hermes/cache/delegation/subagent-summary-*{timestamp}*` (саммари текущего запуска)
   **НЕ удалять:** `final_analysis.md`, `competitor_screenshots.zip`, общий кэш (`~/.hermes/cache/web/`, `~/.cache/ms-playwright/`)

### Именование
```

{domain}--{page_name}--tablet.png

`page_name` — path URL без `/`, fallback `main`. Пример: `example-site.ru--catalog--desktop.png`

```

## Обработка ошибок

- **Конкурент не найден** — спросить у пользователя
- **web_extract ошибка** — пропустить, зафиксировать
- **Playwright не загрузил** — пропустить, отметить в логе
- **Парсер вернул неполные данные** — Критик на доработку (макс. 3 круга)
- **Лимит concurrent** — очередь по 2-3
- **SearXNG недоступен** — fallback на web_search

## Common Pitfalls

1. **Playwright headless** — Chromium установлен. Пути и зависимости: см. `references/setup.md`.
2. **GPU crash на full_page** — тяжёлые страницы (длинный лендинг) могут крашнуть GPU. Решение: отдельный `browser` на каждую страницу, DPR=1 для всех вьюпортов.
3. **Мобильные редиректы** — фиксировать m.domain.
4. **web_extract обрезка** — проверять длинные страницы.
5. **Вес архива** — full_page PNG 1920px = 5-13 МБ за скрин. 48 скриншотов ~100-150 МБ. Если слишком большой — JPEG (quality=85).
6. **`--` в именах** — не `::` (Windows).
7. **Галлюцинации парсеров** — Критик ОБЯЗАТЕЛЕН.
8. **Факт-чек** — Критик проверяет критические данные (цены, контакты, УТП) через web_search.
9. **Иероглифы в отчётах** — LLM могут вставлять китайские/японские/корейские символы. Критик ОБЯЗАТЕЛЬНО проверяет и заменяет на русский. Директор при финальной сборке — повторная проверка всех текстов.
10. **SearXNG** — POST, не GET. Яндекс — лучший для Runet.
11. **page_name** — path URL без `/`, fallback `main`.
12. **Провайдеры** — модели выбираются через clarify. Провайдер должен быть настроен в Hermes. См. `references/setup.md`.
