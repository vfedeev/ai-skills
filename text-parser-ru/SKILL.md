# Text Parser RU — чистка текста по образцу пользователя

Пользователь (дизайнер, работает с текстами макетов, расшифровками, выгрузками) даёт «грязный» текст и один эталонный фрагмент, который он привёл в порядок руками. Задача — найти в остальном тексте те же дефекты и исправить их так же, не выдумывая лишних изменений.

## Когда триггерить

- «Почисти текст / приведи к нормальному виду / убери переносы и ¶ вот по этому образцу».
- «Убери иероглифы / китайские символы» и «сделай типографику: кавычки-ёлочки, тире, пробелы» — готовые пресеты, секция ниже (эталон не нужен).
- Пользователь прислал файл или кусок текста с OCR-мусором, артефактами вёрстки, битыми абзацами — и фрагмент-эталон, как должно быть.
- Просьба «продолжить чистку» после предыдущего куска того же документа.

Не триггерить: стилистическая правка/переписывание (это humanizer-ru, adv-checkup), транскрибация аудио (ai-transcribe), извлечение данных в таблицу.

## Готовые пресеты (работают без эталона)

Если эталона нет и просят типовой операции, не угадывай стиль: это готовые пресеты — чистка CJK (иероглифов) и русская типографика. Правила общепринятые (Русская типографика / ГОСТ 7.5), применяются напрямую; спорные места — как обычно в список вопросов.

### CJK — чистка от иероглифов

`python3 scripts/strip_cjk.py вход выход --remove --map`

Без флагов скрипт работает как аудит: счётчики по группам Unicode и проблемные строки — сначала смотри аудит, потом меняй. `--map` — безопасно конвертирует полноширинные знаки и CJK-пунктуацию в обычные; `--remove` — удаляет иероглифы/кану/хангыль (следы машперевод/кривого копипаста) и подчищает висячие пробелы. В список вопросы если: иероглифы несут смысл (бренд, имя, цитата) и аудит не уверен; найдён mojibake (битая кодировка) — скрипт подсказывает это отдельно, лечится иначе.

### ТИПО — русская типографика

`python3 scripts/typo_ru.py вход выход`

Ровно три операции по правилам русского языка: `"..."` → `«…»` (вложенные `'...'` → `„…“`), ` - ` и `--` между словами → ` — `, числовые диапазоны `5 - 7` → `5–7`, `...` → `…`; пробелы убираются перед `, . ; : ! ? % ) ]` и после `( [`. Незакрытые кавычки скрипт не угадывает — они идут в отчёт «unclosed», а отчёт — в список вопросов. Дефис внутри слова (`тест-драйв`) и маркеры списков `- ` в начале строки не трогает.

Если в задаче есть эталон пользователя, он главнее пресета: пресет — только для того, что эталон не покрывает; расхождение фиксируется в заметке.

## Рабочий процесс

### 1. Принять вход

Вход — текст в чате или файл (txt, md, docx — читать через read_file, PDF — через ocr-and-documents). Сохрани сырой текст в `$BH_AGENT_WORKSPACE/raw.txt` как есть, не правя: он нужен для диффов и отката.

### 2. Разобрать эталон

Эталон — это ТЗ в форме примера. Сначала глянь `references/log/`: если этот клиент/формат уже чистился, правила берутся оттуда и только сверяются с эталоном. Сравни эталон с его же «до»-версией в сыром тексте и выпиши список конкретных правил вида «`<паттерн>` → `<замена>`», а не абстрактное «навести порядок». Типовые паттерны:

- жёсткий перенос строки внутри предложения → склеить через пробел;
- `¶` / `§` / `%` в конце строк (артефакт абзаца из вёрстки) → удалить символ, перенос абзаца оставить один;
- лишние пробелы перед знаками препинания, двойные пробелы, табы;
- удалённые пользователем скобки/кавычки/звёздочки Markdown, нумерации, маркеров списка;
- дефис-переносы (`пе-\nренос`) → склеить;
- склеенные без пробела слова после переноса строки.

Полный каталог паттернов и способы проверки — в `references/patterns.md` (читать на шаге 2, сверяться при незнакомых артефактах).

Если эталона нет — не угадывай стиль: если запрос покрывается готовым пресетом (иероглифы/типографика — секция выше), это шаг 3 без эталона; иначе спроси, показав 2–3 варианта исправления одного спорного куска.

### 3–5. Исполнение: ОДИН вызов конвейера

После шага 2 весь остаток цикла — один запуск:

`python3 scripts/pipeline.py raw.txt <профиль> out-prefix [--attach-short] [--docx]`

Внутри конвейера: base-нормализация (BOM/CR/¶/soft-hyphen/дефис-переносы) →
`run(t)` профиля (правила из эталона) → ТИПО-пресет (quotes / [dashes] / spaces) →
`POST(t)` → регресс-чек нулями из `CHECKS` → пишет `out-prefix--clean.txt`,
с `--docx` — ещё `.docx` (¶/↵/отбивки) тем же processом. Exit code 1 = чек
провален — починить профиль. exit 0 = СДАВАТЬ СРАЗУ: отдельная сверка глазами,
диффы, повторные прогоны-проверки — только для нового класса или по просьбе
пользователя (скорость первична; правки пользователь внесёт запросом).

Профиль — `references/profiles/<класс>.py` (контракт в docstring pipeline.py;
зрелый пример: `afisha.py` — воспроизводит принятый v2 побайтово за 1 вызов).
Если класса ещё нет — анализ и написание профиля это и есть шаг 2; сама чистка
всё равно остаётся одним вызовом. Новый проверенный профиль = копить в profiles/.

Править однотипные места глазами в файле >50 строк запрещено. Жёсткое правило
остаётся: трогать только то, что объясняется выписанным правилом; орфографию,
стиль, порядок слов, содержимое — не менять.

### Спорные места — список вопросов разом

Если паттерн похож на эталонный, но применение правила меняет смысл или неясно, чистить ли это место (например, `¶` между заголовком и абзацем vs внутри списка), не молча выбирай вариант и не спрашивай по одному вопросу. Собери ВСЕ спорные места в один нумерованный список вопросов через clarify: каждый вопрос = цитата «до», предлагаемый «после» и, если уместно, второй вариант. Пользователь отвечает один раз — дальше доделываешь по его решениям. Спрашивать ДО конвейера, не после: решения входят в профиль одним прогоном.

### 5. Выдать результат

- Короткий текст → исправленный текст прямо в чат (без комментария вокруг, если не просят).
- Длинный или был файл → сохранённый файл в workspace, имя через `--` (двоеточия нельзя на Windows): `исходник--clean.<расширение>`. В чате — путь + 2–3 строки итога (что менялось, сколько правок).
- **Формат отдачи = формат, который несёт договорённое форматирование.** Простой `.txt` не перевозит: мягкие переносы внутри абзаца (↵ vs ¶), неразрывные пробелы (NBSP), разные тире (дефис/–/—), отступы и стили. Если правки затрагивают хоть что-то из этого — отдавай `.docx`/`.odt`/`.rtf`/`.html`, не txt. Word-структура (¶/↵/отбивки) — флаг `--docx` конвейера (внутри build_docx_schedule, без pandoc: из txt pandoc не различает ¶ и ↵). Другие пары форматов — `pandoc` установлен на сервере (`pandoc --list-output-formats`). Рабочую txt-копию всё равно оставляй в workspace.

### 6. Зафиксировать задачу

После сдачи — обязательный шаг: одна заметка на каждую завершённую задачу в `references/log/` (имя `ГГГГ-ММ-ДД-тема.md`, см. шаблон в `references/_template.md`): источник, найденные паттерны, принятые решения по спорным местам, пример до/после, ссылка на скрипт если писался. Это память скилла: при новом запросе «дошлифуй тот же формат» сначала просмотри `references/log/` — правила прошлого раза применяются сразу, без нового эталона.

## Чего не делать

- **Смысловые правки текста — только через явный запрос к пользователю.** Любое изменение, касающееся слов, а не оформления (название зала/фамилия/термин: «Каминный» vs «Камерный», опечатка в слове, падеж, порядок слов, состав предложения), — не менять молча даже если «явно опечатка»: показать место и спросить. Скилл меняет только форматирование, типографику и структуру абзацев; содержимое неприкосновенно до решения пользователя. Найденное расхождение (как «Камерный зал» в эталоне vs «Каминный зал» в тексте) — в список вопросов, и ответ фиксируется в log.
- Не выдумывать паттерны «для полноты»: нет уверенности — в список вопросов (шаг 4).
- Не перезаписывать исходник: сырой текст остаётся в raw.txt, результат — отдельный файл.
- Не предлагать своё оформление вместо эталона пользователя.
