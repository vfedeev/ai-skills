# Масштабирование дизайна

Три этапа; начинать нужно с того, который соответствует состоянию проекта:

- **0. ФП + выводы проекта + тексты + фрэнки → ч/б композиционный прототип → первая
  Hi-fi-концепция.** Подготовительный этап, когда собственной утверждённой Hi-fi-концепции
  ещё нет: прототип и концепция согласуются отдельно, после утверждения этап А снимает с неё
  правила. ФП задаёт структуру и содержание, фрэнки — композицию, таблица выводов —
  эмоциональные и визуальные требования. Фрэнки не является источником чужих цветов,
  шрифтов, графики или текстов. Подробности — `references/stage-0.md`.
- **А. Концепция → правила + UI-kit.** Один раз на проект: измерить утверждённую концепцию,
  записать правила в `дизайн-правила.md`, собрать UI-kit в Figma. — `references/stage-a.md`.
- **Б. Прототип + тексты (+ фрэнки) → дизайн-макет страницы.** Для каждой новой страницы.
  Макет собирается на английской версии текстов, русская копия — после согласования;
  изображений агент не генерирует — заглушки с промтом внутри. — `references/stage-b.md`.

> Смежное: извлечение ДС сайта/макета в git-канон (tokens.json DTCG → Figma → манифест → DESIGN.md) — скилл `ds-creator` (поглотил ds-extraction и brand-dna-extractor 23.11.2026).

Главный принцип: каждое значение на новой странице — из концепции или из правил. Если
концепция на вопрос не отвечает, агент принимает решение сам, но называет его в отчёте
и не выдаёт за правило.

Второй принцип: **каждый цвет в UI-kit и на страницах привязан к цветовой переменной** —
заливки, обводки, цвет текста, стопы градиентов, тени, скрытые слои и служебные подложки.
Работа не закончена, пока `scripts/color-audit.js` не вернёт `unbound = []`.

Третий принцип: **текст на страницах живёт файловыми TEXT-стилями.** До наполнения секций —
создать сет стилей по типорампe UI-kit (если их нет — это дефект файла, чинится перед
сборкой) и ставить `textStyleId` на каждый TEXT-узел; инлайн-маркеры заголовков (нумерация
«NN/») — range-оверрайды (`setRangeFontName`/`setRangeFontSize`) внутри стилизованного узла.
Правки кегля/интерлиньяжа/цвета в процессе макетирования вносятся **в стиль, не в узлы** —
значения меняются руками дизайнера, стиль надо пересоздать/поправить и перепривязать, а не
править десятки узлов. Итоговый стиль фиксируется после показа ручной правки.

## Среда исполнения

- **Claude Code** (основной путь): Figma через подключение claude.ai — `use_figma`,
  `get_screenshot`, `get_metadata`; перед первым вызовом загрузить скилл `figma-use`, для
  UI-kit — ещё `figma-generate-library`, для страницы — `figma-generate-design`. Выполнять
  их инструкции как есть.
- **Hermes Agent**: Figma через MCP `figma-console-cloud` (плагин Desktop Bridge).
  Маппинг инструментов, пейринг, особенности relay и скриншотов — `references/hermes-env.md`;
  прочитать до первого `figma_execute`. `figma-use` остаётся обязательной прембулой и здесь.

## Какой этап и что прочитать

До первого действия прочитать нужные файлы целиком:

| Задача | Читать |
|---|---|
| Создать первую концепцию, если своей утверждённой ещё нет | `references/stage-0.md` + `references/frankie.md` (если есть фрэнки); дополнительно найти таблицу выводов в файлах проекта |
| Снять правила и UI-kit с концепции | `references/stage-a.md` + `references/colors.md` |
| Собрать страницу по прототипу и текстам | `references/stage-b.md` + `references/colors.md` |
| То же, и к странице есть фрэнки | `references/stage-b.md` + `references/frankie.md` + `references/colors.md` |
| Только привязать цвета или проверить привязку | `references/colors.md` |
| Шрифты концепции недоступны или концепция на внешней библиотеке | `references/fonts.md` (+ `references/colors.md`, «Концепция на библиотеке») |
| Собрать/пополнить базу фрэнки, отобрать кандидатов под блоки ФП | `references/frankie-base.md` |
| Вход страницы — фото рукописного скетча | `references/sketch.md` + `references/stage-b.md` |

Страницу просят, а `дизайн-правила.md` и страницы Figma «UI-kit» нет:
- есть утверждённая собственная концепция — сначала этап А;
- концепции ещё нет — сначала этап 0, затем после утверждения этап А.
Не пытаться выполнить этап Б без дизайн-правил и UI-kit.
Все пути в файлах — от папки скилла.

## Входной гейт — до первого действия

| Вход | Откуда |
|---|---|
| Фрейм концепции (этапы А/Б) | ссылка с node-id; нет ссылки — спросить, есть ли утверждённая концепция; нет — этап 0 |
| Функциональный прототип (этапы 0/Б) | фрейм/секция в Figma или `.md`: блоки по порядку и состав каждого. Обязателен; фрэнки не заменяет ФП |
| Тексты (этапы 0/Б) | фрейм «Тексты», `.md`, `.docx`, Google Doc; несколько языков — макет на английском; лежат рядом, ссылку не дали — спросить, брать ли |
| Фрэнки (этапы 0/Б) | фрейм в Figma с фрагментами референсов по блокам; пользователь в файле — найти самому, ссылку не запрашивать |
| Бриф, материалы бренда, таблица выводов (этап 0) | описание проекта, брендбук; таблица «эмоции → слой дизайна → приёмы» — искать в файлах проекта |

Входы на месте — прогнать четыре проверки; любая провалена → список вопросов дизайнеру,
работа не начинается (не «начинаю с допущениями»):

1. ФП читается: блоки по порядку, состав и количества явно извлекаемы; не читается — вернуть на доработку.
2. Критерии приёмки страницы определены (этап Б): состав блоков, язык макета, что не трогать.
3. Противоречий между ФП, текстами и фрэнки не осталось; найденные — в вопросы до сборки.
4. `дизайн-правила.md` в папке относится к этому проекту (строка «Источник»): чужой — не перезаписывать, положить новый в подпапку с именем проекта.

Файл правил — в папку проекта рядом с прототипом; папки нет — в текущую, путь назвать в отчёте.

## Границы операций

| Всегда | Спросить сначала | Никогда |
|---|---|---|
| привязывать цвет при создании элемента; DRY_RUN перед настоящим запуском скрипта; аудит после каждой привязки; обновлять статус-файл | снять стили/компоненты библиотеки и заменить ролями; перезаписать существующий фрейм (или собрать v2); сократить или перевести тексты; вписать приём в файл правил | трогать фрейм концепции; менять гарнитуры в стилях самому; генерировать изображения; молча нормализовать разнобой; брать со фрэнки шрифты, цвета, тексты, картинки |

## Гейты и лимиты

- **Сломанный гейт = не проверено.** Ошибка скрипта, пустой вывод, отключённый плагин —
  не зачёт. Не смог проверить → черновик.
- **Control case на первый аудит сессии:** `color-audit.js` по концепции, где ничего не
  привязано, обязан вернуть непустой `unbound`; `qa-geometry.js` по макету с заведомой
  поломкой — ненулевой `issueCount`. Неработающую проверку нельзя отличить от
  отсутствующей: сначала починить ROOT_IDS/скрипт, потом принимать.
- **Циклы ограничены:** bind→audit по одной секции — не более 3 итераций; два неудачных
  точечных исправления одного узла — пересобрать секцию из чистого клона, третий патч
  не накладывать. Лимит исчерпан → черновик со списком причин.
- **Приёмка (перед словом «Готово»):** `color-audit` `unbound = []` + `qa-geometry`
  `issueCount = 0` + `offScale` из `inventory.js` пуст или каждая позиция названа в отчёте +
  количества по блокам соответствуют ФП + каждый фрагмент текстов на странице или назван
  в отчёте + концепция и исходные фреймы не изменены (ревизия сверена со статус-файлом).

## Статус-файл

`<проект>/дизайн-статус.md` — рядом с правилами, по `assets/status-template.md`.
Создаётся на этапе А, обновляется на этапе Б по каждой странице: статусы страниц с
цифрами гейтов, карта блоков с evidence, известные проблемы, открытые вопросы, счётчик
«где выбирал сам», ревизия Figma на момент «утверждаю». Записанное — претензия, проверяемая
сверкой с живым состоянием Figma перед действием. Одинаковый выбор «сам» в третий раз →
предложить правило в раздел «Предлагаю добавить в правила». Аппрув привязан к ревизии:
концепция изменилась после «утверждаю» — ре-аппрув.

## Отчёт

Состав и формат разделов — `references/report.md`. Критично: первая и последняя строки
отчёта — статус («Готово» / «Черновик, не закончено:» с перечнем); числа раздела «Цвета» —
только вывод скриптов (JSON-выдержка), не пересказ агента.

## Частые ошибки

Ошибки этапов и цвета — в конце каждого файла из `references/`. Общие:

| Ошибка | Как правильно |
|---|---|
| Начал работу, не определив, есть ли утверждённая концепция | выбрать этап 0 или А по состоянию проекта |
| Начал работу, не прочитав файл этапа и `colors.md` | сначала таблица «Какой этап и что прочитать» |
| Вернул оригинальные шрифты до привязки цветов текста | сначала `color-audit.js` = 0, потом гарнитуры |
| Сам поменял гарнитуру в стилях, чтобы скрипт прошёл | попросить дизайнера вернуть замены |
| Пересоздал текст и потерял ширину колонки | переносить `minWidth`/`maxWidth`: в концепциях ими держат 320 и 680 |
| Задал тексту `paragraphSpacing` или межстрочный «как в оригинале» | любое типографское свойство отвязывает стиль — значение вносить в сам стиль |
| Назвал готовым то, что не прошло проверки | сдать черновиком с перечнем, что осталось |
| Взял со фрэнки шрифт, цвет, текст или картинку | фрэнки даёт только композицию, значения — из правил (`references/frankie.md`) |
| Концепция на стилях библиотеки, а агент молча снял стили или молча оставил их | спросить один раз до UI-kit (`references/colors.md`, «Концепция на библиотеке») |
| Принял пустой вывод `color-audit.js` за «всё привязано» | control case: по концепции вывод обязан быть непустым |
| Чинил один узел в третий-четвёртый раз | лимит: два провала → пересобрать секцию из чистого клона |
| Задал крупному тексту фиксированную ширину и не проверил переносы | Display-текст молча переносится (5 строк становятся 6): проверить число строк = height/lineHeight и ужимать fontSize циклом, пока не уложится |
| Задал прозрачность пилюли/плашки на frame, а не на paint | `fills:[{...,opacity}]` на самом прямоугольнике, не `frame.opacity` — иначе текст-потомок тоже полупрозрачный |
| Проверил макет только сравнением скриншотов | сначала программная геометрия `scripts/qa-geometry.js` (issueCount = 0), затем vision-сверка |
| Сдал первую в проекте страницу без независимой сверки | этап Б, шаг 7.5: проверяющий без контекста сборки |
| Перенёс референс-страницу по набору текстов и сделал композицию «свою» | сначала разбери DOM референса в браузере: `getComputedStyle` ключевых блоков (position/top залипающей навигации, scroll-spy, якоря `a[href^="#"]`, раскладка колонок) — в макете повторяй расположение и поведение, а не только состав; визуальный стиль референса не бери |
| Вынес нумерацию/маркеры секций в отдельную колонку «в стиле файла» | сними сетку с существующих страниц файла (x-позиции TEXT-узлов через REST) и ставь края блоков на колонки; короткие маркеры веди внутри заголовка одним текстовым узлом с range-шрифтами (`setRangeFontName`/`setRangeFontSize`), отдельный «рельс» под них сетку ломает |
| Писал в канвас, пока юзер вручную правит макет | со слов «я правлю вручную» — прекратить все write-вызовы до показа результата; список найденных мелочей — в статус-файл, возврат к правкам после фиксации стиля |
| Сдал макет на сырых типографских значениях («стилей в файле нет») | текстовые узлы — только через файловые TEXT-стили: сетка стилей создаётся до наполнения секций; после ручной правки дизайнера значения переносятся В СТИЛЬ (он следует сам), не в отдельные узлы; заметка-инвентарь слотов — в notes проекта |

### Особенность этапа 0: работа в текущем Figma-файле

Ч/б прототип создаётся в открытом файле пользователя: не запрашивать и не отправлять
ссылки на файл или фреймы, сообщить только название фрейма и готовность к правке. Пока
пользователь редактирует — не трогать прототип. После его сигнала — заново изучить
актуальный фрейм (не прежний снимок), сверить с ФП и фрэнки, получить подтверждение
композиции, и только затем согласовать направление и Hi-fi. Подробности —
`references/stage-0.md`.
