# Search & Analyze — исследование, делегирование, факт-чек

Единый скилл глубокой аналитики: планирование → сбор (solo или fan-out) → агрегация → hard-гейт фактчека по claims → отчёт. Тело — скелет и маршрутизация; техничные детали — в `references/`, механика — в `scripts/` (прогрессивное раскрытие).

## When to Use (триггеры)

- «проведи исследование / глубокий / многоисточниковый поиск по теме X»
- «собери актуальные данные + факт-чек»; «сравни X и Y»; «кто лидер рынка Z»; «найди цены / фичи / бенчмарки»
- аналитический отчёт / обзор / датасет из веб-источников
- факт-чек о **человеке/персоне**; анализ интервью/подкаста/YouTube-канала (атрибуция цитат, цели автора)

Активируй без точной формулировки, если подразумевается проверка из нескольких независимых источников. Для персоны/интервью ОБЯЗАТЕЛЬНО сначала `references/persona-factcheck.md`.

**Анти-триггеры (мимо этого скилла):** одиночный quick-поиск (зови `web_search`), конкурентный бриф лендинга (отдельный скилл брифинга), интерактив с пользователем в процессе сбора — субагенты не умеют задавать вопросы, уточнения собирай ДО fan-out.

## Шаг 1. Планирование

- Чек-лист плана в `.hermes/plans/*.md`: подвопросы → инструменты → ожидаемый вывод. Декомпозиция — по ОСИ пользователя («какой стек» = состав; «насколько» = эффект; не подменять). Правка в полёте важнее исходной рамки: пересобирай затронутые задачи, не всю волну.
- 1 аспект = 1 задача, без пересечений; 5+ аспектов → 2 волны. Follow-up «есть ещё X?» — отдельная волна с exclusion-списком уже включённого («НЕ повторяй: …»), тот же ledger и папка.
- **Unified vs fan-out по формуле**, не по вкусу: если весь материал помещается в `context_window − prompt − response buffer` — один агент (он видит противоречия между частями); сверх окна — fan-out (цена: cross-файловая слепота детей).
- **Заморозь task contract до первой генерации** (для всей волны, идентичный каждому ребёнку): scope, бюджет (≤N источников, ≤M поисков), acceptance + mandatory-отказы, stop rule. Rubric с весами и проходным баллом фиксируется ДО сбора; правка рубрики после просмотра кандидатов = новый эксперимент: версионировать и перескорить всех.
- **Shared ground truth инжектируется строкой** в каждый промпт (актуальная дата, перечень уже известных фактов, exclusion-список) — считать один раз оркестратором, не ссылкой на файл (иначе N независимых чтений и N шансов увидеть stale).
- Рабочее состояние — файл снапшот (`research.json`: ledger claims, seen-множество, состояние волн). В контекст истории дописывай снапшот в ХВОСТ (после существующих сообщений), не переписывай голову — перезапись сбивает cached prefix всего прогона.

## Шаг 2. Сбор

**Solo** (1–3 подвопроса) — собираешь сам, всё ниже применимо к одному агенту.
**Orchestrator** — batch `delegate_task`, все диспатчи в одном ответе. Механика (поля tasks, лимит параллельности из конфига, option-маршруты, зонд провайдера, атомарность JSON, steer/stop, ledger) — `references/delegation-ops.md`. Промпты — по `references/subagent-template.md`, анти-галлюцинационный контракт обязателен в контексте каждого ребёнка: данные только из инструментов, ни фактов/цифр/URL из головы, «не найдено» вместо домысливания.

- **Бюджет — часть задачи:** каждый delegate = cost-нода, оправдай измеримым выигрышем (наивный мульти-агент стоит 3–10× одного). Read-heavy черновое — на дешёвый маршрут, синтез — на дорогой. В каждый subtask — явный кап итераций и exit criteria: без них у зависшего цикла нет границы стоимости. Оценку стоимости считай по сериализованному payload, не chars/4 (для кода/не-латиницы недооценка 23–35%, а для бюджета опаснее переоценки).
- **Лог промптов:** перед каждым provider-вызовом — блокирующая запись промпта ребёнка и пути результата в persistent-каталог исследования (`research/prompts/NNN-<slug>.md`, timestamped). Не throw при сбое лога. Это база для постмортема упавшего промпта и cost-аудита.
- **Watchdog:** при живом батче раз в ~3 мин `action='list'` + tail live-транскриптов; нет активности два check подряд (~6 мин) — сразу доложить пользователю причину (завис на аппруве/провайдер 429/долгий fetch), новые волны до выяснения не диспатчить. Полная процедура — `references/delegation-ops.md` §Watchdog.
- **Детям не выдаём sudo и aprovable-операции** (subagent_auto_approve=false — ребёнок на них встаёт молча): такие шаги делает только оркестратор; SUDO_PASSWORD из .env в контекст детей не попадает никогда — см. delegation-ops §Подтверждения.
- **Pipeline vs barrier:** следующая стадия нуждается во ВСЕХ результатах предыдущей → барьер; иначе — конвейер (быстрее в ~3×). Возобновляемость прерванной волны обеспечена только детерминизмом оркестратора (никаких rand() и current-time внутри цикла — состояние из снапшота).
- **loop-until-dry:** волны сбора останавливаются после K=2 пустых раундов; множество `seen` ОБЯЗАНО включать отвергнутые источники/claims, иначе цикл не высохнет.

## Шаг 3. Агрегация

- **Аудит файлов детей перед сшивкой:** скан модельных артефактов (CJK-глифы, «приклеенная» латиница в русском) по деливераблу, не по summary; каждая `[n]`-цитата требует пункт `[n] <URL>` в источниках; файлы без домена → декларация базы URL; ссылки на scratch (24 ч) — как воспроизводимые по URL. Ингестить только после completion-уведомления ребёнка.
- Дедуп по полному URL; пометки `relevance` (high/medium/low) и `needs_check`.
- **Каждое утверждение, нагружающее вывод, заводится в claims-ledger** (`templates/claims_ledger.json`): id, формулировка, source_urls, status (начальный `UNKNOWN`), verification_note, attempts. Отсюда же proof log финального отчёта.
- Табличные данные + нужна обработка → субагент `jupyter-live-kernel`.

## ⛔ Шаг 4. Факт-чек-гейт (hard gate — блокирует Шаг 5)

> Синтез запрещён, пока гейт не пройден. Ошибка атрибуции или непроверенный ключевой факт в отчёте недопустима (инцидент: цитата гостьи «13 лет женаты» приписана ведущей).

- **4.0** Факт-чек обязателен при любом проверяемом факте (число, дата, статус, цитата, атрибуция). Персона/интервью → сначала `persona-factcheck.md`.
- **4.1 Инвентаризация:** все `needs_check` + нагружающие claims из ledger в реестр проверки (что проверить, чем подтверждается сейчас).
- **4.2 Adversarial-волна (верификатор ≠ сборщик):** вторая волна детей получает задачу **опровергнуть**, а не подтвердить. Против ложного консенсуса: верификатору — claim + источники БЕЗ аргументации сборщика. Требование: минимум 1 независимый источник вне контроля субъекта; ключевые цены/даты/бенчмарки — 2 подтверждения. **Majority vote ≠ проверка**: частота упоминания в источниках не закрывает непроверенное требование. Цитаты — исполняемо: `scripts/fetch_quote.py <URL> "<фраза>"`; остальные рецепты (SPA/help-центры, GitHub, геосторы, bot-wall) — `references/verification-recipes.md`. Видео/соцсети — `youtube-content`; блок 429 — `references/youtube-429-recovery.md` (цепочка backoff→player_client→invidious→метаданные; НЕ цитировать «должно быть в видео»). Сверка атрибуции реплик обязательна.
- **4.3 Конфликт источников** → хронология или явная метка «противоречиво»; проверка числовой состоятельности (возраст vs стаж брака).
- **4.4 Эскалация до закрытия или лимита попыток:** новые домены, archive.org, точные цитаты, аудитория. **3 провала на claim → статус `known_issue`/data_gap в ledger и дальше; ни одна неудача не исчезает молча.**
- **4.5 `clarify`** при неустранимой неопределённости по материально важному факту: что считать базой, копать ли дальше. НЕ угадывать под удобный вывод.
- **4.6 Критерий прохождения:**
  - каждый нагружающий claim в ledger имеет статус `CONFIRMED` / `REFUTED` / `UNKNOWN` + `verification_note`; `CONFIRMED` — только по воспроизводимому check (re-fetch/grep/evidence-файл), не по мнению верификатора;
  - high-impact/спорные claims — judge panel: ≥2 независимых верификатора, повторять пока разброс оценок ≤1.5 или бюджет исчерпан (остановка по бюджету ≠ приёмка, фиксируется отдельно);
  - обязательные (mandatory) критерии рубрики: «нет первоисточника — не CONFIRMED для персоны», «самозаявление — не независимое подтверждение» — провал дисквалифицирует статус при любом балле;
  - proof log отчёта: каждая строка ledger, включая `REFUTED` и непрошедшие (`UNKNOWN`), версии рубрики и команды проверки;
  - калибровка гейта (разово, при изменении рубрики): прогнать заведомо passing- и failing-кейс через шаги 4.2/4.6, ложные accept/reject заносятся в историю скилла.

## Шаг 5. Синтез и доставка (только после гейта)

Отчёт (Markdown): Executive summary/TL;DR (с оговоркой по дырам) → секции по подвопросам со ссылками → сравнительная таблица/вердикт (если применимо) → таблица источников (relevance, status) → **таблица уверенности = выгрузка ledger (CONFIRMED/REFUTED/UNKNOWN)** → Open questions / Data gaps (ничего не удаляем молча). Источники, недоступные напрямую (сниппеты, стены), помечены явно.

- Сохрани `.md` (`write_file`, имя на латинице, `~/` или рабочая папка), сообщи путь. В футере — честная стоимость: попытки/ретраи/время; метрика качества прогона — **cost per accepted** (принятый результат с учётом провалов), проваленные попытки входят.
- Деливерабл = заметка vault (если назвал): правила скилла `obsidian`, датированно, без дублей; следующие волны — в ту же заметку.
- TL;DR / экспорт сырых данных (JSON/MD из ledger) / cron-обновление — по запросу.

## Pitfalls

1. Ребёнок без лимита выводов тонет: «верни 5–7 выводов», период поиска обязателен (умолчание — 12 мес.).
2. Язык ответа не указан — вернёт английский.
3. Два ребёнка ищут одно — объединяй задачи.
4. Сбой одного — остальные прикрывают, логируй и продолжай.
5. Free-модели: rate limit при >5 детей, склонны выдумывать — ссылки обязательны.
6. Широкий goal («обзор AI») — сужай до «цены и фичи 5 инструментов для X за 2026».
7. Исследование без файла = несуществующее; всегда .md + ledger на диске.
8. Жирное тело скилла платится каждый turn сессии — поэтому детали вынесены в references/, открывай по таблице выше, не читая всё подряд.
