# Операции делегирования (открывать: Шаг 2, перед диспатчем волны)

## Batch-механика

```python
delegate_task(tasks=[
    {"goal": "...", "context": "...", "option": "fast"},
    {"goal": "...", "context": "...", "option": "deep"},
])
```

- Все диспатчи в одном ответе = параллельно. Схема `tasks` принимает `goal`/`context`/`output_schema`/`images`/`option` — полей `toolsets`/`role`/`model` нет; дети наследуют дефолтные тулсеты, ограничивать их можно только текстом в `context`.
- Параллельно — не больше `delegation.max_concurrent_children` (сверить с конфига, не хардкодить): `terminal("hermes config show | grep -iA6 delegation")`, если пусто — `search_files(pattern='^delegation:', path='~/.hermes/config.yaml', context=8)` (длинные строки через шелл-пайпы обрезаются).
- **Держи конвейер полным:** `action='list'` показал свободные слоты — сразу диспатчь очередь следующей волны, не дожидаясь всей текущей — дети на подписочном плане дешёвы, простой слотов дороже.
- Живой контроль батча: `action='list' / 'steer' / 'stop'` с `subagent_id` из ответа spawn.
- `tasks` — строгий JSON, батч валидируется атомарно: одна битая вложенность в `output_schema` (например, у array-поля пропущен `items`) убивает ВЕСЬ dispatch с неинформативным «could not be parsed». Держи схемы минимальными (файл-путь + пара полей), прогоняй JSON на валидность до отправки.

## Маршруты моделей (option)

- fast/medium — сбор фактов, поиск по одному сервису, форматирование; deep — синтез, тяжёлый фактчек, разбор противоречий; coder/senior-coder — скрипты-проверки; review/senior-review — независимая приёмка деливерабла; vision — картинки.
- Имена маршрутов смотреть в `delegation.backends.*.options` конфига, не выдумывать.
- Подписочный план не списывает деньги за детей — маршрут выбирать по задаче, не ради экономии; спрашивать «платить ли за детей» не нужно.
- Бесплатные OpenRouter `:free` — legacy-fallback, только когда настроенный провайдер недоступен и дети нужны срочно; список free-моделей живёт на Windows-десктопе, на сервере fallback — дефолтный `delegation.provider`.

## Зонд провайдера

Первый вызов каждого ребёнка платит спавном; если провайдер умер/без баланса, весь батч падает за секунды с 429/400. Перед фан-аутом — тривиальный зонд-ребёнок (или проверка баланса): дёшево всего, заодно валидирует `option`-маршрут.

## Ledger

Ledger — собственность оркестратора: в контекст детей явно пиши «НЕ редактируй ledger.json» — прямые записи детей минуют нормализацию URL (запись с trailing slash ломает `sources.py verify` с сообщением, где обе строки выглядят идентично). Лечение — прогнать ledger через `normalize_url` скрипта, см. pitfall в `grounded-citations`.

## Watchdog волн (каждые ~3 минуты)

Пока батч жив, оркестратор не «ждёт результат», а контролирует:

1. Раз в ~3 минуты — `delegate_task(action='list')` + `tail -c 400` по логам `live_transcripts` (каталог delegation cache, `live/<deleg_id>/task-N.log`). Рост лога = активность.
2. Нет активности два проверки подряд (~6 мин) — **сообщить пользователю причину сейчас**, не дожидаясь конца волны: статус из `list` (running/idle/completed/interrupted) + последняя строка транскрипта как диагноз (завис на подтверждении/апруве, провайдер 429/400, долгий fetch/скачивание).
3. Пока причина не ясна — новые волны не диспатчить; `steer` с уточнением или `stop` + перезапуск суженной задачи по watchdog-диагнозу.

## Подтверждения и sudo — детям недоступны

`subagent_auto_approve=false`: ребёнок на aprovable-команде встанет молча (спросить пользователя он не может). Поэтому: **в goal детей не включать операций, требующих подтверждения** (sudo, внешние записи, установки). **SUDO_PASSWORD (из .env) в контекст детей не передаётся НИКОГДА** — даже по «кажущейся» нужде. Такие операции — только оркестратору, в обычном порядке, с обычным апрувом пользователя; ребёнку вместо этого отдай уже готовый результат («УЖЕ ПРОВЕРЕНО ОРКЕСТРАТОРОМ»).
